# Вопросы к защите

## Зачем отдельный initContainer, если веса лежат на PVC?

PVC хранит уже загруженные веса между перезапусками Pod. InitContainer проверяет их по ревизии, списку файлов и SHA256. Если проверка проходит, он заканчивает работу до импорта Hugging Face SDK; если нет, скачивает новую ревизию во временный каталог и проверяет её перед заменой активной. `HF_HUB_OFFLINE=1` у сервера запрещает ему обращаться к Hub, но это настройка приложения, а не сетевой запрет Kubernetes.

## Почему модель запускается с `float32`?

Это настройка текущего CPU-стенда, не заявление, что такой dtype быстрее всех. Результат зависит от CPU, сборки PyTorch/vLLM, памяти и точности, которую допускает модель. Здесь выбранный режим зафиксирован для сравнимости; другой dtype сначала нужно проверить на совместимость и качество, затем измерить на той же машине.

## Что делают prefill и decode?

Prefill обрабатывает входной prompt и создаёт KV-cache. Decode выдаёт ответ токен за токеном, используя этот кеш. Длинный вход увеличивает работу prefill и обычно задерживает первый токен; длинный ответ дольше занимает decode.

## Чем отличаются `max-num-seqs` и `max-num-batched-tokens`?

`max-num-seqs` ограничивает число последовательностей, которые движок может обслуживать одновременно. `max-num-batched-tokens` задаёт бюджет токенов в одном batch, в том числе для prefill. Поднятие числа последовательностей может увеличить throughput при очереди запросов, но одновременно повысить задержку каждого клиента. Сравнивайте настройки парными сериями, а не по одному удачному прогону.

## Что ограничивает KV-cache?

KV-cache хранит ключи и значения внимания для активных последовательностей. Чем длиннее контекст и больше одновременных запросов, тем больше памяти требуется кешу. Если памяти не хватает, могут упасть доступное число последовательностей или стабильность запуска; увеличение бюджета кеша имеет смысл только при наличии свободной памяти Pod.

## Какой результат настройки удалось подтвердить?

При восьми клиентах с коротким входом увеличение `max-num-seqs` с 4 до 8 подняло throughput с 28,38 до 47,86 выходных токена/с (+68,7%). p95 latency снизилась с 8,80 до 5,18 с. При лимите 4 часть клиентов ждёт свободной последовательности; лимит 8 сокращает это ожидание. Направление выигрыша совпало в обоих повторах. Для длинного входа бюджет 4096 вместо 2048 дал -5,0% и +1,7% throughput в разных повторах, поэтому устойчивый выигрыш не подтверждён. Базовые значения оставлены прежними; короткий профиль стоит выбирать под такую же нагрузку, а не объявлять универсальной настройкой.

## Как измеряется TTFT?

Клиент начинает отсчёт перед HTTP-запросом и останавливает его на первом непустом `delta.content` в SSE-потоке. Chunk только с ролью ассистента первым токеном не считается. Поэтому TTFT включает loopback, port-forward, очередь и обработку prompt, а не только вычисления модели.

## Что доказывает p95 в этом отчёте?

Каждая строка сводки объединяет 60 запросов из двух повторов. Nearest-rank p95 — 57-е значение в отсортированном ряду: `ceil(60 × 0.95) = 57`. Это описание хвоста задержек конкретного прогона на общей рабочей станции. Двух повторов недостаточно для оценки устойчивого production SLO. Поэтому рядом показан разброс throughput повторов, а в A/B второй повтор меняет порядок условий. Вывод о настройке сильнее, если направление разницы сохраняется в обоих повторах.

## Kubernetes Secret шифрует токен?

Нет. Base64 в представлении Secret не является шифрованием. Доступ ограничивают права на сам объект и API Kubernetes; локальная копия токена в `.secrets` исключена из Git и получает ограниченные права на файле там, где платформа их поддерживает. Для настоящего кластера отдельно настраивают хранение Secret и права доступа согласно его среде.

## Что даёт HMAC в журналировании?

`serve.py` принимает событие от дочернего процесса только при верной подписи и допустимой схеме. Случайный ключ существует лишь в процессах одного запуска; это мешает обычному тексту или поддельному JSON пройти фильтр. HMAC подтверждает подпись, но не шифрует журнал и не защищает от процесса, который уже получил ключ.

## Зачем закреплять базовый образ и Python-пакеты?

Тег образа сам по себе может со временем указывать на другой набор слоёв, поэтому базовый образ закреплён digest. Lock-файл фиксирует полный список дистрибутивов; сборка сверяет его и останавливается при пропуске, лишнем или изменённом пакете. Это упрощает повторение сборки, но не доказывает безопасность каждого upstream-компонента.

## Короткая демонстрация

Нужен уже запущенный прогретый кластер. В первом терминале оставьте port-forward:

```powershell
python tools/local.py forward
```

Во втором проверьте Pod, отправьте запрос и выполните один короткий прогон. Потребуется два терминала, поскольку `forward` остаётся на переднем плане:

```powershell
python tools/local.py status
python tools/client.py "Explain what a Kubernetes initContainer does."
python tools/local.py benchmark --label reduced-smoke --requests 1 --repeats 1 --concurrency 1 --workload short --output bench/demo.json
```

Сводка базового прогона хранится в [bench/summary.json](../bench/summary.json), условия A/B-серий — в [bench/experiments/manifest.json](../bench/experiments/manifest.json). Для обсуждения результатов откройте таблицы README вместе с сырыми измерениями и снимками конфигурации.
